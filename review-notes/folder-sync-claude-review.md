**Verdict: decisions needed first.** The transport and recovery sections (plan lines 29–45) are sound and implementable. Section 1 (lines 21–27) names the right problems but leaves three design choices open that determine the sync schema, and the current code contradicts two of the plan's assumptions. Settle findings 1–3 before writing any migration.

## Findings

**1. High. Decide who owns derived sessions before designing identity.** Plan lines 10 and 23–27 say to sync "normalized activity needed to retain/recalculate time" and also to sync sessions with a Source Machine. It never says whether a receiving machine re-derives sessions from imported activity or stores the sender's session rows verbatim. These lead to different schemas. Confirmed code: detection depends on per-machine idle timeout (`session-service.ts:438-440`) and on local-timezone midnight clipping (`session-detector.ts:208-228`). Failure scenario: desktop in Chicago and laptop in London both derive from the same activity and produce different boundaries, so `claudeSessionId|startedAt` keys (`session-service.ts:671,698`) never match, edits attach to different rows on each machine, and the Source Machine column is meaningless for re-derived rows. Minimum change: state that sessions are owner-authoritative. Only the device that observed the transcript derives, reconciles, and republishes its sessions; receivers store them as-is and never run detection over remote activity. Activity events sync only for prompt timing and duplicate suppression.

**2. High. Rescans destroy the identities the plan intends to preserve; the reconciliation step is a prerequisite, not a sub-bullet.** Confirmed code: an incremental scan deletes every auto session for a changed file and reinserts fresh rows with no edit carry-over at all (`session-service.ts:512-563`). Rebuild carries only `projectId`, `clientId`, `description` (`:665-676`), so `billable` is lost. Invoice line items store comma-separated integer session ids (`invoices.ts:52`, `invoice-service.ts:576,691`); only `purgeExcludedSessions` spares invoiced rows (`:141-160`), scan and rebuild do not. Failure scenario: user marks a still-open transcript's session non-billable and adds a description, the next 20-second scan runs, and both are gone before sync ever sees them. Minimum change: replace delete/insert with a match-and-update pass keyed by `(sourceFile, claudeSessionId)` plus interval overlap; matched rows keep their id and user fields; unmatched rows that carry edits or invoice references are kept and flagged for review rather than deleted. Plan line 23 should say this explicitly and sequence it as step 0 with its own tests, because sync cannot be trusted until local rescans stop churning ids.

**3. High. Activity identity is not defined and Codex cannot support the plan's own rule.** Plan line 25 correctly says path and line number are insufficient, then defers the design ("validate first"). Confirmed code: Claude messages have a real uuid (`session-parser.ts:63`); Gemini and OpenCode use provider message ids; Codex synthesizes `uuid = l${idx}` from the line index (`codex-parser.ts:346`). Raw-message dedup keys on `(source_file, uuid)` (`session-service.ts:1536`) where `source_file` is an absolute per-machine path, so a copied transcript is a different file and imports twice. Failure scenario: the same Codex rollout is copied to the laptop and continued differently on both machines; line 412 on each machine is a different event with the same fingerprint, so one machine's tail is silently dropped as a duplicate. Minimum change: define the activity key as `(tool, providerConversationId, eventId)` where Codex `eventId` becomes a hash of timestamp + type + payload, and drop `source_file` from the cross-device identity. Ownership rule for copied transcripts under finding 1: a device derives sessions only from events it published first, so an identical copy yields nothing and a divergent tail yields a distinct session.

**4. High. Local cleanup must not become a synced deletion.** Plan line 36 adds explicit deletion records; line 27 says imported activity must survive local cleanup, but nothing says local cleanup must not publish tombstones. Confirmed code: disabling a provider deletes all its auto sessions (`session-service.ts:85-116`) and exclusion rules delete rows (`:137-188`); `purgeExcludedProjects` deletes projects (`client-project-service.ts:388`). Failure scenario: user turns off Codex tracking on the laptop; if deletion is hooked at the delete call, the desktop imports tombstones and loses its Codex history. Minimum change: tombstones are emitted only from the user delete path (`deleteSession`, client/project delete UI), never from purge or rescan, and the owner's reconciliation pass must consult local tombstones so a deleted auto session is not re-detected on the next scan (today `deleteSession` at `:974-986` leaves nothing behind and the row returns).

**5. Medium. Project identity collides with the `directory_path` UNIQUE NOT NULL constraint.** Plan line 14 makes paths machine-specific, but projects are keyed by path (`projects.ts:12`, `client-project-service.ts:338-371`) and sessions bucket for hours and earnings by `projectId` (`earnings.ts:129-134`). Failure scenario: laptop clones the repo to a different path, `autoCreateProject` mints a second project, and two agents working the same project across machines are billed twice because overlap merging is per bucket. Minimum change: move paths to a `project_device_paths` table (or make `directory_path` nullable and drop the unique index), give projects a sync uuid, and when a local auto-create would produce a name matching exactly one unmapped synced project, link instead of create. Plan line 43 already promises the prompt; the schema change is what is missing.

**6. Medium. "Wait and retry on missing dependencies" has no exit.** Plan line 34. Failure scenario: a writer's batch is lost (user pruned Drive storage, upload failed before the laptop was wiped) and every later batch from that writer blocks forever. Minimum change: per-writer sequence numbers plus a periodic per-writer snapshot, and a rule that a gap older than N days is resolved by importing the newest snapshot. Also state what an older app does with a newer protocol version: stop importing that writer and show "update required", not skip, since skipping also creates a gap.

**7. Low. Clone detection needs a concrete trigger.** Plan line 31 says a cloned install gets a new writer id but not how it knows. Minimum: store the last published sequence locally and in the writer directory; on startup, if the folder shows sequences beyond the local counter for my device id, treat this install as a clone and mint a new id before publishing.

## First-version simplifications

- **Owner-authoritative sessions** (finding 1) removes cross-device conflicts on measured fields entirely. Conflicts are limited to description, billable, project/client links, manual sessions, clients, and projects.
- **Per-field last-writer-wins by Lamport revision** instead of parent-revision conflict queues (plan line 41). Edit-versus-delete resolves as undelete. For one person with two machines this preserves "never overwrite newer with old" without a conflict UI.
- **No dependency waiting.** With LWW records and one writer per directory, batches apply in any order; sequence gaps only warn.
- **Sync activity as events without content** (uuid, timestamp, type, tokens, model). Rows are already content-free (`raw-messages.ts`), so storage growth is modest.

## Missing acceptance tests

- Disable a provider on B; A retains that provider's history (finding 4).
- Delete an auto session on A, rescan its file on A; it stays deleted on both machines (finding 4).
- Edit description and billable on a session of a still-growing transcript, run an incremental scan; id, edits, and invoice line item references survive (finding 2).
- Same Codex rollout copied and continued differently on both machines; both tails appear as distinct sessions (finding 3).
- Change the owner machine's timezone and rescan; edits survive the shifted midnight split (findings 1, 2).
- Same repo at different paths on both machines; Human Hours and earnings count overlapping work once (finding 5).
- Delete one writer batch from the folder; the other machine still imports later batches or recovers from a snapshot (finding 6).
